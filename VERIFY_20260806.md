On a genuinely fresh device the signing key doesn't matter (nothing to upgrade over). If you
ever install over an existing build, use the same release keystore or `-r` fails and the

# Phase 3 — OpenBubbles migration (one-shot)

### Why it's one-shot

`retireOpenBubbles()` deletes `/data/data/com.openbubbles.messaging` in `migrate()`'s `finally`,
and `ob_migration_done` is set in the launcher's SharedPreferences (`smarttxt_flags`) — *"reset
only by wiping the app's data."* Whatever isn't copied is gone: the migration reuses OB's
registration, so Apple treats that history as already delivered and won't backfill.

If you need to reset later: `adb shell pm clear com.offlineinc.dumbdownlauncher` (better than
uninstalling — leaves the APK alone). Then restore and re-sign-into OpenBubbles.

### What's being verified

Two fixes that have **never run on a device**, both cases where the feature worked and
surrounding machinery undid it. **The offline harness cannot see either** — it never runs
`create()` or the Compose gates. That's how both shipped.

**Fix A — the import was wiped 1.1 s after it landed.** `SmartTxtRepository.create()` clears
the store once per install (flag `purged_demo_cache_v2`). On a migrating device that first
`create()` is triggered by `markRegisteredExternally()`, which `migrate()` calls immediately
*after* the import:

```
15:51:31.626  history verify: SQLite reads back 4 room(s), 22 message(s) ✓
15:51:32.694  purged leftover demo chat cache (first native run)
15:51:33.486  cache restore: 0 room(s), 0 message(s)
```

`ObHistoryImporter` now claims that purge — runs it *before* writing and sets the flag.

**Fix B — the handle picker appeared anyway.** `SmartTxtApp` used `remember { mutableStateOf }`,
which captures at first composition — while the migration is still running, since that
composable renders `MigrationScreen`. Now `LaunchedEffect(status)` re-reads on `REGISTERED`.

### Already proven (offline only)

Four real OB stores including a 28-chat / 643-message one → 24 rooms / 512 messages. LMDB walk
byte-identical to `liblmdb` across all 12,239 entries of a 3.5 MB store. 6/6 unit tests.
Send-from reads correctly from both prefs shapes.

### Watch for, in order

```
relation Chat.(unnamed)#1→e7: N pair(s) (forward)
history rooms: built N … N from the handle relation, 0 recovered from senders
history verify: SQLite reads back N room(s), M message(s) ✓
════ ✅ HISTORY IMPORTED: N room(s), M message(s) ════
send-from: carried OpenBubbles' '…' → … (post-login picker skipped)
```

**Pass** — all five, then **no** `purged leftover demo chat cache` *after* the import (fix A),
`cache restore:` with **non-zero** counts, **no** handle picker (fix B), and messages actually
visible in the chat list.

**Fail**

| Line | Means |
|---|---|
| `⚠️ HISTORY IMPORT FOUND NOTHING` | stop, capture everything |
| `0 chat↔handle pair(s)` | relation didn't decode — check `relation probe:` |
| `0 from the handle relation, N recovered from senders` | relation broke, fallback caught it; history lands but groups may be member-narrow |
| `cache restore: 0 room(s), 0 message(s)` after a good verify | **fix A failed** |
| handle picker appears | **fix B failed** |

Two `suCopy … FlutterSharedPreferences.preferences_pb exit=1` warnings on OB 1.15.0 are
expected — that build only has the XML, read successfully right after. Worth quieting so it
stops looking like an error in support bundles.

Attachment migration is not implemented; attachment-only messages are skipped on purpose (their
files live in OB's data dir, which the uninstall wipes).

# Phase 4 — Google Messages: duplicate bubbles

### The bug

One send, two bubbles — nothing is actually sent twice, recipients get one. `sendText` inserts
an optimistic row keyed `tmp_<nanoTime>`; the phone's echo replaces it by matching `gm.tmpId`.
**After a re-link the echo comes back with an empty tmpId**, so the server copy is appended
beside the optimistic one, and the distinct ids mean it survives everything after.

### Scope, deliberately narrowed

This only stops **new** duplicates. Rows already doubled on a customer's phone stay doubled —
a decision, not an oversight. The restore-time cleanup was written and then **removed**: it
meant a de-duplication pass over restored history on every launch, and history is the one thing
in this app that has already been lost once. Customers who want them gone can Log out and back
in, which clears the store.

### ⚠️ On a fresh device you may not reproduce this at all

The suspected cause is stale send-identity: `outgoingIdByRoom` merges on restore and never
replaces, while `requestConversationList(count = 25)` refreshes only 25 threads at session
start — so threads beyond the first 25 keep their **pre-re-link** `defaultOutgoingId`. Tristan
had 64 local rooms; the other customer had 86.

**A fresh sign-in creates at most 25 local rooms.** All 25 refresh on the next session, nothing
goes stale, and the bug may simply never fire. So:

- Sign into an account with **many** conversations, and give it activity so local rooms build
  past 25 before you re-link.
- If you can't get past 25, run the test anyway — the logs still tell you something valuable
  (below), because the competing hypothesis doesn't need >25 threads.

### The test

1. Sign into Google Messages (done in Phase 2). Let it sync.
2. **Re-link phone** — Settings → Re-link. *Not* Log out; Log out clears the state that sets
   the bug up.
3. Send in a thread that is **not** among the 25 most recent.

```bash
adb logcat -c && adb logcat GMRepo:W MsgStore/gmessages:I GMSession:D '*:S'
```

### Read the result — this table is the point of the exercise

| What you see | Means | Verdict |
|---|---|---|
| `dedup-fallback: echo had no tmpID, reconciled by body+time` and `saved:` goes `X → X+1 → X+1` | the bug fired and the fix caught it | ✅ **fix proven** |
| no `dedup-*` line, `saved:` goes `X → X+1 → X+1` | the echo carried its tmpID — the bug never happened | ⚠️ **not reproduced**, fix unexercised. Not a pass. |
| `dedup-miss: outgoing echo matched nothing`, `saved:` goes `X → X+1 → X+2` | bug fired, fallback did **not** catch it | ❌ **fix insufficient** — capture and stop |

That middle row is the trap: on a fresh device "no duplicates" is the expected result whether
the fix works or not. Only `dedup-fallback` proves anything.

**If you get `dedup-miss`, the `tmpId` field settles a long-running question.** Empty → the
stale-send-identity theory is right, and Tier 2 of `GMESSAGES_DOUBLE_BUBBLE_FIX.md` is worth
shipping (re-sync all cached rooms after a re-link instead of 25). Populated but matching
nothing → a different cause, two repository instances alive in one process, and Tier 2 does
nothing for it.

### Why this can't be seeded with mock data

Worth knowing so nobody spends an hour on it. The remaining fix only fires when a real echo
arrives from Google without its tmpID — a protocol condition, not local state. And the
precondition (a thread outside the 25 Google re-syncs) is decided by Google's ordering of the
real account, not by rows in SQLite. Seeding the store would have tested the restore-time
cleanup, which no longer exists.

# Phase 5 — Google Messages: silent receive-slot loss (Alex's bug)

### The bug

Google gives an account **one receive slot per device type** (1 web, 2 tablet, 1 PWA — we
register as tablet). `SetActiveSession` returning 200 means "accepted", not "you are the
receiver". The flag latched on that 200 and was only cleared by a transport failure or a
restart, so a displaced device looked identical to one nobody had texted.

Alex's capture, 18h21m of silence from `08-04 21:00:31`: 251 acks before, 5 after — and all 5
fire 2–20 s after a registration, i.e. they ack our own. Three reconnects before the cutoff
showed `startup ack count=11 / 7 / 7`; the **75** after were **all** `count=0`. Zero
`AuthExpired` / `reauth` / `SESSION_COOKIE_INVALID` in 370,239 lines. The final heartbeat still
says `alive`.

**What changed:** we now handle the `USER_ALERT` we were discarding (`BROWSER_INACTIVE` →
bounded reclaim, capped at 3 within a decay window so two live devices can't evict each other
forever); a 30-minute re-assert as backstop; and auto-unpair on every teardown path.

```bash
adb logcat -c && adb logcat GMSession:D GMGaia:I '*:S'
```

`GMSession:D` is in both diagnostics filterspecs, so these reach a submitted bundle. The logout
line is tagged `GMGaia`, which is in the **rolling** logs but stripped from the hourly snapshot
— use rolling.

### 5a. The re-assert fires and stays quiet

Leave the phone idle 35+ min.
✅ exactly one `re-asserting active session [up 35m, last inbound 35m ago]` →
`setActiveSession re-asserted OK`.
❌ more than one per 30 min, or a reconnect screen appears.

### 5b. Auto-unpair — cleaner on a fresh device than it would be otherwise

Because you signed in on the new build, this pairing has a **stored pairing-attempt id from the
start**, so the revoke should work on the very first re-link. (On an existing customer phone the
first re-link logs `unpair: no stored pairing-attempt id` — correct, not a failure, and the
one after that revokes.)

Count entries in Google Messages → profile picture → **Device pairing** on your Android
smartphone. Re-link the flip (this is the same re-link as Phase 4 — do both in one pass).
Recount.

✅ count unchanged (old gone, new added) + `unpair: revoked pairing 3f2a1b8c… (HTTP 200)`.
❌ count goes up by one, or `Google REJECTED the revoke`.

### 5c. Log out doesn't hang

Airplane mode ON → Log out.
✅ sign-in screen within ~3 s, `unpair: revoke failed to send`. Force-stop, reopen: ✅ still
sign-in, not chats.
❌ anything longer, or a button that looks dead.

### 5d. Back out mid-logout

Press Log out, then immediately press End. Wait 10 s. Reopen.
✅ sign-in screen. ❌ the chat list — that's the race being closed.

### 5e. Displacement — the actual Alex repro, needs a second flip

A browser probably won't do it: a browser takes the WEB slot and we register as TABLET. With
phone A receiving, pair phone B to the same Google account and text it.

```
user alert BROWSER_INACTIVE (#1) — Google says another session took the receive slot; reclaiming it now
setActiveSession re-asserted OK
user alert BROWSER_ACTIVE — this device is the receive target
```

Bounce to `#4`: ✅ `Not reclaiming again` and it stops fighting.

*Worth trying anyway:* if a **browser** displaces the flip, that's a separate bug — our TABLET
registration isn't taking effect — and worth chasing.

# Known-open, not blocking

- `waitForSimAndPhone` polls forever with no escalation (30× / 4m44s observed).
- `PairingAPI: reportVersion: HTTP 404` on every launch — the endpoint doesn't exist.
- `relink` can take ~28 s on a captive portal (`reauth()` 25 s + unpair 3 s). Better than the
  old unbounded hang, but it wants a spinner.
- The message-cache save loop can outlive `cache.clear()`, so history can survive a Log out.
  `shutdown()` now cancels before clearing, which narrows it; closing it needs a fence like
  `GoogleMessagesSessionClient.storeWritable`.
- `staleReplayRemaining` decrements before the waiter dispatch, so our own RPC responses consume
  replay slots. Low impact — every capture so far shows `startup ack count=0`.
- Session interval bookkeeping is wall-clock, not `elapsedRealtime`.
- The Cowork VM's `/sessions` volume is at 100%. `repos/_corten_tmp/` is full of 0-byte husks
  (the bridge can't delete) plus a stray `.writetest`. Clear it from a real terminal.
